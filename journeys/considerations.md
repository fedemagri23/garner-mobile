# Considerations

Deliberate limits, trade-offs and simplifications, and when to revisit them.
Notation as in the backend's `journeys/README.md`: ids are sequential and never
renumbered; a superseded entry stays and gains a **Superseded by:** line.

## Foundation

### MCON-001 — The API client is generated from the backend's committed contract
- **Phase:** 1 · **Area:** api · **Status:** accepted
- **What:** `src/api/schema.d.ts` is generated by openapi-typescript from `garner-app/openapi.json` and committed; calls go through openapi-fetch, typed by path. CI regenerates it from the backend's master and fails on any difference.
- **Why:** The backend lives in another repository; a generated client turns a breaking API change into a compile error here. openapi-fetch is a thin typed `fetch`, so there is no generated runtime code to review. openapi-typescript runs from a pinned throwaway install because it supports only TypeScript 5 and the app is on 6.
- **Revisit when:** The backend publishes the contract as a versioned package, or the app must support an older API version than master.

### MCON-002 — Only one token refresh runs at a time
- **Phase:** 1 · **Area:** session · **Status:** accepted
- **What:** The token manager refreshes ahead of expiry and after a 401, and every caller that needs a token while a refresh is running waits for that one refresh. A request that still gets a 401 after one refresh and one retry is the caller's to handle; the session is gone by then.
- **Why:** The backend rotates refresh tokens and treats a reused one as theft, revoking every session of the account. Two concurrent refreshes would sign the user out everywhere.
- **Revisit when:** The backend's rotation rules change.

### MCON-003 — The web target keeps the session in memory
- **Phase:** 1 · **Area:** session · **Status:** accepted
- **What:** On iOS and Android the refresh token is in the keychain/keystore (`expo-secure-store`). On web, which has no secure storage, it is held in memory and a reload signs out.
- **Why:** Web is a development convenience, not a product target; putting a long-lived credential in `localStorage` would make it one script injection away from theft.
- **Revisit when:** A web app becomes a product — then it wants an httpOnly-cookie session from the backend instead.

### MCON-004 — Fonts load at runtime, not embedded
- **Phase:** 1 · **Area:** theme · **Status:** accepted
- **What:** Bricolage Grotesque and Figtree load with `useFonts` from the `@expo-google-fonts` packages behind the splash screen. A font that fails to load falls back to the system font rather than blocking the app.
- **Why:** Runtime loading works in Expo Go, so development needs no custom build yet. Embedding with the `expo-font` config plugin is faster at launch but needs a development build.
- **Revisit when:** The first development build is made (phase 2 needs one for the camera) — switch to the config plugin then.

### MCON-005 — Copy is Spanish only, with no i18n layer
- **Phase:** 1 · **Area:** whole app · **Status:** accepted
- **What:** Strings are written in Spanish (es-AR) inline in the components.
- **Why:** The launch market is Buenos Aires; an i18n framework before a second language exists is structure without a user.
- **Revisit when:** A second language or market is planned — extract strings then, before the app grows further.

### MCON-006 — The API's error messages are English; screens translate what they expect
- **Phase:** 1 · **Area:** errors · **Status:** accepted
- **What:** The backend writes error messages in English. A screen passes Spanish wording for the statuses it knows the meaning of (409 on sign-up means the email is taken); anything unexpected shows the server's English message.
- **Why:** Mapping statuses per screen is enough for the handful of errors each flow can produce, and needs no backend change. Showing raw server text to Spanish-speaking users everywhere is not acceptable; translating server sentences on the client would break the first time one is reworded.
- **Revisit when:** A screen needs to tell apart two errors with the same status (validation on several fields), or a second language arrives — then the backend should send stable machine-readable error codes for the app to translate.

### MCON-007 — "Near me" is the phone's position first, the saved place second
- **Phase:** 2 · **Area:** location · **Status:** accepted
- **What:** The app asks for location once, uses a fix up to five minutes old, and falls back to the place saved in preferences when the phone says no. With both available, the chip on Inicio switches between them; the choice lasts until the app closes and is not saved. The phone's position is never written to preferences, and the radius is the one saved there (5 km by default).
- **Why:** Prices near where you stand are the point of the app, but a shopper planning from home needs their usual area too. Saving a position the person did not choose to save would be surprising, and a remembered choice is not worth a preference field yet.
- **Revisit when:** Profile settings arrive (later phase) — choosing and naming the saved place, the radius, and remembering the choice belong there.

### MCON-008 — Search results show no "desde" price
- **Phase:** 2 · **Area:** search · **Status:** deferred
- **What:** The mockup shows each result's lowest nearby price. Results show brand and package instead; prices appear on the product screen.
- **Why:** `GET /v1/products` carries no prices, and fetching a comparison per row would be twenty requests a page.
- **Revisit when:** The backend can answer a page of products with each one's lowest price near a point, in one request.

### MCON-009 — The 30-day chart ends yesterday and averages every store
- **Phase:** 2 · **Area:** product · **Status:** accepted
- **What:** The chart on a product shows the backend's daily history across all stores, which is aggregated once a day. A price that fell today shows in "Cerca tuyo" and in "Bajaron cerca tuyo" but not in the chart until tomorrow, and the chart's trend can read "subió" while today's price is lower.
- **Why:** The daily history is what the backend keeps long-term; mixing today's current prices into it would put a different kind of number on the last bar. Only stores near the shopper would need a history per store, one request each.
- **Revisit when:** Shoppers read the chart as contradicting the drop — then add a "hoy" bar from the current prices, marked as such, or ask the backend for history limited to nearby stores.

### MCON-010 — A product screen route in each tab that opens one
- **Phase:** 2 · **Area:** navigation · **Status:** accepted
- **What:** `(home)/product/[id]` and `search/product/[id]` both render the same `ProductScreen`, so a product opens on top of the tab it was tapped in and back returns there.
- **Why:** Each tab has its own stack; one shared route outside the tabs would hide the tab bar and lose the tab's place.
- **Revisit when:** A third tab needs it (lists, in phase 3) — consider Expo Router's shared groups, `(home,search,lists)`, instead of another file.

### MCON-011 — Prices are shown in their own currency, never converted
- **Phase:** 2 · **Area:** prices · **Status:** accepted
- **What:** Every amount is formatted with its own currency — "$ 1.390" for pesos (centavos only when there are some), "€ 1,15" for euros (always with cents), the ISO code for anything else — in the Spanish style the app is written in. The product screen compares each price only with the cheapest in the same currency, and its chart asks for the history in the currency of the prices near the shopper. Nothing is converted.
- **Why:** The demo data now has a Vienna neighbourhood in euros beside the Buenos Aires one in pesos. A comparison across currencies would need exchange rates, and a shopper compares the shelves in front of them, which share one currency.
- **Revisit when:** Number formatting follows the device's locale rather than the app's language, or a list or plan spans countries.

### MCON-012 — The scanner reads retail codes, matched as scanned
- **Phase:** 2 · **Area:** scanner · **Status:** deferred
- **What:** The camera looks for EAN-13, EAN-8, UPC-A and UPC-E, and the code goes to `GET /v1/products/barcode/{code}` exactly as read. A code can also be typed, which is how the web build and a phone without camera access use it.
- **Why:** These are the codes on supermarket shelves; QR and the rest are noise there. The catalog's codes are EAN-13.
- **Revisit when:** Products are catalogued from UPC-A codes. iOS reports a UPC-A as a 13-digit EAN with a leading zero and UPC-E arrives compressed, so the same product can read as two different strings — the backend should store and look up GTINs in one normalized form.

### MCON-013 — "A la lista" adds one at a time, and lists open in phase 3
- **Phase:** 2 · **Area:** lists · **Status:** accepted
- **What:** From a product, "A la lista" shows the shopper's lists with their item counts and how many of this product each already has. A tap adds one: a new line the first time, one more on the existing line after that. With no lists, it offers to create "Mi lista" in the currency of the prices nearby. The Listas tab, where lists are seen and edited, is phase 3.
- **Why:** Adding from where you find a product is the habit the mockups design for, and the counts in the sheet are enough to see that it worked. One line per product keeps the list readable and the optimizer's input simple.
- **Revisit when:** Phase 3 builds the Listas tab — quantities, notes and removal belong there.

### MCON-014 — A scanned product always opens in Buscar
- **Phase:** 2 · **Area:** navigation · **Status:** accepted
- **What:** Whichever tab the scanner was opened from, the product it finds opens on Buscar's stack.
- **Why:** Scanning is a way of searching, and a single destination keeps the scanner from needing to know who opened it.
- **Revisit when:** Shopping mode (phase 4) scans during a trip — there the product belongs on the trip, not in Buscar.

### MCON-015 — Back on Expo SDK 57 until Expo Go 58 is in the stores
- **Phase:** 2 · **Area:** tooling · **Status:** deferred
- **What:** The app was started on SDK 58 and moved back to SDK 57 (React Native 0.86, React 19.2, expo-router 57, jest 29). The only code change was the native tabs import, `expo-router/unstable-native-tabs` on 57.
- **Why:** SDK 58 shipped on 2026-10-15, and Expo said its Expo Go would reach the App Store and Play Store "within a few weeks". The developer's iPhone has Expo Go 57.0.9, which refuses an SDK 58 project, and a development build on iOS needs a paid Apple developer account. Nothing the app uses is new in 58.
- **Revisit when:** Expo Go for SDK 58 is in the App Store — then upgrade (`npx expo install expo@~58.0.0 --fix`, the import back to `expo-router/native-tabs`, `jest`/`jest-expo` to their 58 versions), run expo-doctor and every check, and mark this resolved. Store Expo Go supports only the latest SDK, so waiting too long breaks Expo Go again.

### MCON-016 — A list item's price is set when it is added
- **Phase:** 3 · **Area:** lists · **Status:** accepted
- **What:** A product added to a list gets, as its expected unit price, the cheapest price near the shopper in the list's currency at that moment; none if nobody near has reported one. The list's "Total estimado" adds those up and says how many items have no price. Prices are not refreshed afterwards.
- **Why:** The backend keeps the expected price on the item, and the real answer to "what will this cost" is the optimization in checkpoint 5, which reads current prices at real stores. A cheap, stable estimate is enough for the list screen.
- **Revisit when:** Checkpoint 5 lands — the list can then show the latest optimization's total instead, or refresh expected prices when it runs.

### MCON-017 — No manual reordering yet, and whole quantities only
- **Phase:** 3 · **Area:** lists · **Status:** deferred
- **What:** Items appear in the order they were added; − and + change the quantity by one, and − at one removes the item. The backend supports a manual order (`PUT …/items/order`) and fractional quantities, but the app offers neither.
- **Why:** Drag to reorder needs gesture work out of proportion to its value before shopping mode exists; and weighed products (0,5 kg) need a different input, not a stepper.
- **Revisit when:** Shopping mode (phase 4) — the order of a trip matters there, by store aisle, and weighed products are bought there.

### MCON-018 — The web dev server can serve stale screens after edits
- **Phase:** 3 · **Area:** tooling · **Status:** accepted
- **What:** With `npm run web` running, Metro sometimes keeps serving a screen's previous code after the file changed (screens load lazily on the web). Restarting with `npx expo start --web --clear` fixes it.
- **Why:** A development-server quirk, not app behaviour; it cost two debugging detours before being recognised.
- **Revisit when:** A newer SDK fixes lazy route invalidation — until then, restart with `--clear` before trusting what the web build shows, and before `npm run e2e:web`.

### MCON-019 — A plan is asked for on each visit, and Inicio shows the last one
- **Phase:** 3 · **Area:** plan · **Status:** accepted
- **What:** Opening "¿Dónde conviene comprar?" requests an optimization from where the shopper is, and polls it every second until it is done. Inicio's card shows the latest finished plan of the most recently changed list that has items, with when it was calculated ("Calculado hoy"); it does not calculate one by itself.
- **Why:** The backend answers the same question from its answer of the last 15 minutes, so asking on every visit is cheap and keeps prices current. Calculating from Inicio on every launch would spend the worker's time on lists nobody is about to shop.
- **Revisit when:** The card's "Calculado" date is often old — then refresh it in the background when Inicio opens and the last plan is more than a day old.

### MCON-020 — The web build draws the trip without a map
- **Phase:** 3 · **Area:** plan · **Status:** accepted
- **What:** On the phone, the stops are on a real map (`react-native-maps`: Apple Maps on iOS, Google Maps on Android, included in Expo Go). On the web, where that library does not run, the same positions are drawn to scale on a plain background, without streets.
- **Why:** The web build is for development and the automated walk-through; a web map library would be a second map implementation to maintain.
- **Revisit when:** The app ships to Google Play — Android store builds need a Google Maps API key (Expo's "Deploy app with Google Maps" steps); Expo Go does not.

### MCON-021 — "Minimum saving per extra stop" is not editable in the app
- **Phase:** 3 · **Area:** plan · **Status:** deferred
- **What:** Preferences in the app cover what to show first, the most stores, extra distance and extra time. The fourth limit, the least an extra stop must save, keeps its default (400 cents) and has no control.
- **Why:** The backend stores it as one amount in cents for every list, whatever its currency: 400 is $ 4 for a peso list and € 4 for a euro list, which no single control can present honestly.
- **Revisit when:** The backend keeps that limit per currency, or as a percentage of the list's total.

### MCON-022 — Shopping needs a connection until checkpoint 7
- **Phase:** 4 · **Area:** trip · **Status:** resolved
- **What:** Every tick, price and status change goes straight to the backend. The screen changes at once and puts a line back if the request fails, but nothing is kept for later: without a connection, ticks fail.
- **Why:** The plan splits phase 4 in two: the trip itself first, then the persisted outbox that replays changes in order when the connection returns (the spec's §27).
- **Revisit when:** Checkpoint 7, next.
- **Resolved:** by checkpoint 7 — see MCON-025.

### MCON-023 — A trip is fixed when it starts
- **Phase:** 4 · **Area:** trip · **Status:** accepted
- **What:** A trip copies the list (and, from a plan, the plan's stores and prices) when it starts. Starting again while one is in progress for that list returns the one in progress, even if a different plan was chosen. Lines cannot move to another store mid-trip, and the price typed is per unit.
- **Why:** The backend keeps a trip as the record of what was planned when the shopper walked in, and refuses to start two at once so a retried tap cannot create a second trip.
- **Revisit when:** Shoppers need to change stores mid-trip, or restart a trip with another plan — that needs a store field on line updates (garner-app CON-046).

### MCON-024 — A trip without stores shares no prices
- **Phase:** 4 · **Area:** trip · **Status:** accepted
- **What:** Starting from Compra uses the list as it is, where items usually have no store; prices typed there are kept on the trip but cannot become price reports, since a price needs a store. The summary says so. Starting from a plan gives every line its store, and its prices are shared on "Terminar".
- **Why:** The backend turns a paid price into a report only with its store (garner-app contributions); asking for the store on each tick would slow the trip down.
- **Revisit when:** Shoppers often buy without a plan — then let Compra start a trip at one chosen store (the backend's `storeId`), so those prices count too.

### MCON-025 — Changes on a trip are queued on the phone, in order, and replayed
- **Phase:** 4 · **Area:** offline · **Status:** accepted
- **What:** Every tick, price and trip status change (pause, resume, finish, abandon) is added to a queue and written to the phone before anything is sent, then sent in order. It is retried every 5 seconds while anything waits, when the phone reports a network, and when the app returns to the foreground. Changes to one line merge into one; the server's answer replaces the phone's copy once the queue is empty. The last trip the server described is also kept on the phone, so a trip opens without a connection. The screen always shows the server's trip with the waiting changes on top, and says what waits ("Por enviar" on lines, a banner on top).
- **Why:** Each change is an absolute value, so sending one twice, or again after a lost answer, lands the same state; that is what makes blind retries safe, and what the backend's idempotent updates were built for. The queue is plain data in AsyncStorage (a few small JSON entries), enough for one trip.
- **Revisit when:** A queue outgrows storage (price reports from phase 5 add to it), or retries need backing off: today every wait is 5 seconds, however long the connection is gone.

### MCON-026 — Starting a trip needs a connection, and a new one waits for the last
- **Phase:** 4 · **Area:** offline · **Status:** accepted
- **What:** A trip begins with the server's copy of the list, so Empezar needs a connection. While changes from the previous trip are still waiting to be sent, Empezar is off, since the server would still have that trip open and hand it back. A trip finished offline shows its summary at once and disappears from Compra; after a restart before it reaches the server the summary is not shown again.
- **Why:** Starting offline would need the list on the phone and a way to merge a trip made from a possibly stale copy; most people start a trip with a signal, in the street or at home.
- **Revisit when:** People start trips inside shops with no signal — then keep the lists on the phone and start the trip locally with its own id.

### MCON-027 — Signing out throws away what has not been sent
- **Phase:** 4 · **Area:** offline · **Status:** deferred
- **What:** "Cerrar sesión" erases the queue and the remembered trip along with the session, so unsent changes are lost. Nothing warns about it yet.
- **Why:** The next person to sign in on the phone must not inherit someone else's trip, and sending a signed-out user's changes is not possible.
- **Revisit when:** Sign-out becomes easy to reach by accident (profile and settings, a later phase) — ask first when changes are waiting.

### MCON-028 — "Offline" is the phone's word plus the last request's
- **Phase:** 4 · **Area:** offline · **Status:** accepted
- **What:** The banner says "Sin conexión" when the phone reports no network, or when the last request failed to reach the server. A phone with a weak signal that connects but times out looks online until a request fails; and a server that is down looks like a bad connection.
- **Why:** There is no honest way to know the server is reachable without asking it, and every send is that question.
- **Revisit when:** People are told they are offline when only the server is down — then tell the two apart with a request to the health endpoint.

### MCON-029 — A price report is queued like a trip change, and its photo waits on the phone
- **Phase:** 5 · **Area:** contributions · **Status:** accepted
- **What:** "Enviar precio" puts the report on the same queue as a trip's changes, with its own id as the report's id on the server, so a repeated send lands one report. The photo is copied into the app's documents folder (the picker's cache copy can be cleared by the system) and uploaded when the report is sent; an upload that is done but whose report has to wait is remembered, not repeated. A photo the server refuses (too big, not an image) or one that is gone from the phone does not hold the price back: the price goes without it. Reports from more than 7 days ago are refused by the server and the shopper is told.
- **Why:** The place a price is seen is often a shop aisle with little signal; a price that can only be sent online would not be sent. Keeping the price ahead of the photo reflects what each is worth.
- **Revisit when:** Photos wait so long that the documents folder grows — delete reports' photos older than a week, or compress them further before keeping them.

### MCON-030 — A price can only be reported at one of the nearest six known stores
- **Phase:** 5 · **Area:** contributions · **Status:** accepted
- **What:** The store to report at is chosen from the six nearest to the shopper's position (nearest preselected), with the last known price at each; there is no search, and a store not in the catalog cannot be reported at. The currency is the one of the store's country (pesos for AR, euros for AT and the rest of the euro area).
- **Why:** The backend rejects a price for an unknown store, and most shoppers are standing in the nearest one; a list is faster than a search field, and keeps a report to a place that exists.
- **Revisit when:** Shoppers are in a shop that is not in the catalog (shops added by shoppers is a separate feature not yet planned), or standing between two stores that are both closer than a known third.

### MCON-031 — A report's standing is the server's word, shown as it is
- **Phase:** 5 · **Area:** contributions · **Status:** accepted
- **What:** "Mis aportes" says ACCEPTED as "Ya cuenta", UNDER_REVIEW as "En revisión · no cambia los precios hasta que otros lo confirmen", and REJECTED as "No se aceptó · parecía muy distinto de lo habitual". A brand-new account's first prices usually start in review; nothing in the app lets the shopper appeal or edit one.
- **Why:** The backend decides trust from who reported, how far the price is from the usual one and whether there is a photo (garner-app pricing). The app's job is to say what happened without alarm.
- **Revisit when:** People ask why their price "did not count" — then say why (too far from usual, a new account) and offer to add a photo.

### MCON-032 — An alert is made near where the shopper is when they make it
- **Phase:** 6 · **Area:** alerts · **Status:** accepted
- **What:** "Avisame si baja" creates the alert in the currency of the prices near the shopper, with their current position (the phone's, else the saved place) and their usual radius as its place. The alert keeps that place: it does not follow the shopper to another city, and the three kinds are "baja de un precio", "baja un porcentaje" (5, 10, 15, 20%) and "más barato cerca". The threshold is a price per unit.
- **Why:** The backend compares figures in one currency and judges "near" from a point it stores. A place that moved with the phone would need the backend to track where the shopper is, which it deliberately does not.
- **Revisit when:** Shoppers travel: let an alert be moved to "where I am now", or make a Vienna alert from Vienna by being there — which already works, since alerts are per place.

### MCON-033 — Messages arrive when the app asks, until push
- **Phase:** 6 · **Area:** notifications · **Status:** deferred
- **What:** The inbox loads when Avisos opens and on pull-to-refresh; the badge on the tab asks again every minute while the app is open. Nothing arrives while the app is closed, and nothing here is kept for offline: opening Avisos without a connection says so rather than showing the last messages.
- **Why:** This checkpoint is the in-app half of phase 6. Push needs a device-token store and an Expo push channel in the backend first (checkpoint 10).
- **Revisit when:** Checkpoint 10 lands push; and consider keeping the last page of messages on the phone for offline reading.

### MCON-034 — Quiet hours are converted with today's offset from UTC
- **Phase:** 6 · **Area:** notifications · **Status:** accepted
- **What:** The backend keeps quiet hours as UTC hours; the shopper picks them in the phone's local time, and the app converts with the offset the phone has now. After the clocks change (daylight saving) the same stored hours are an hour off, until the shopper saves them again; and a zone with a half-hour offset (India) rounds to the hour.
- **Why:** The backend has no time zone for a user (garner-app: only stores have one). Adding one is a user-settings feature, not part of alerts.
- **Revisit when:** A shopper's quiet hours drift after a clock change — then keep the user's time zone on their preferences and convert on the server.

### MCON-035 — No toggle for shopping reminders
- **Phase:** 6 · **Area:** notifications · **Status:** accepted
- **What:** The backend has a "shopping reminders" category and a preference for it, but nothing creates reminders yet, so the app does not offer a switch for it.
- **Why:** A control for something that never happens would mislead.
- **Revisit when:** The backend sends its first reminder (e.g. "you have a list and a store nearby") — add the switch then.

### MCON-036 — The push switch is honest about where it cannot work
- **Phase:** 6 (checkpoint 10) · **Area:** notifications · **Status:** accepted
- **What:** The "Avisos en el teléfono" card is disabled with a reason on the web and in Expo Go on Android; on a simulator, or without an EAS project id, turning it on says why it cannot. Expo Go on iPhone is allowed to try.
- **Why:** A switch that looks on but can never deliver is worse than one that says it is not available.
- **Revisit when:** A development build exists: set the EAS project id and drop the "no-project" case.

### MCON-037 — Push has not been run on a phone
- **Phase:** 6 (checkpoint 10) · **Area:** notifications · **Status:** open
- **What:** The app side (permission, token, registration, tap to open) is typechecked, unit-tested for the routing, and exported for both platforms, but never ran against Expo's service or a real device. The backend side is tested against a stand-in (CON-050).
- **Why:** It needs a development build, which needs EAS and, on iPhone, a paid Apple developer account.
- **Revisit when:** The first development build is made; try the steps in docs/checkpoints.md, checkpoint 10.

### MCON-038 — Languages come from typed catalogs; changing language restarts the screens
- **Phase:** 7 (checkpoint 11) · **Area:** i18n · **Status:** accepted
- **What:** Spanish, English and German live in `src/i18n/catalog/<language>/<area>.ts`, read with `t('area.key')` through `i18next`. Keys are type-checked against the Spanish catalog (a typo or a missing translation fails `tsc`), and a test checks the languages have the same phrases and the same `{{placeholders}}`. The language is the shopper's pick, else the phone's, else Spanish. Changing it remounts everything below the provider, so a screen cannot stay half in the old language. On the web the shopper stays on the same screen; on a phone the navigation may restart at Inicio (not yet checked on a device).
- **Why:** Text is written from plain functions as well as components (alert messages, errors, plan wording), so a hook per component would miss some. A remount is blunt but cannot leave stale text. The session and cache sit above the provider and survive it.
- **Revisit when:** A phone check shows the shopper is thrown back to Inicio and that matters, or a screen holds state worth keeping across a change.

### MCON-039 — Dates and money are written by the app, not by `Intl`
- **Phase:** 7 (checkpoint 11) · **Area:** i18n · **Status:** accepted
- **What:** Month and weekday names come from the catalog and prices from `formatPrice` (separators, symbol position and spacing per language), not from `Intl`. In English pesos read `AR$1,390`; in German `1.390 ARS`.
- **Why:** iOS, Android and the web disagree on `Intl` details (Spanish "sep" or "sept", whether pesos show ",00"), and a price must read the same everywhere.
- **Revisit when:** More languages or currencies make the tables unwieldy; then lean on `Intl` and test per platform.

### MCON-040 — Words from the server are still Spanish or English
- **Phase:** 7 (checkpoint 11) · **Area:** i18n · **Status:** resolved in checkpoint 14 (MCON-043), except API error messages and product names
- **What:** Alerts in the inbox are written in the chosen language from facts, but push notifications are Spanish only (CON-049), emails are English, API error messages other than the ones screens map by status are English, and product, brand and category names are not translated.
- **Why:** The server does not know the user's language yet.
- **Revisit when:** Checkpoint 14 sends the locale and the backend writes push and email text in it.

### MCON-041 — Adding products and shops: online first, queued offline, no photos
- **Phase:** 8 (checkpoint 13) · **Area:** community · **Status:** accepted
- **What:** "Agregar producto" opens from a search with no match (and a link under the results), and from a scanned code the catalog does not know, with that code filled in. It shows `/v1/product-suggestions` matches first. A brand typed that matches a listed one (ignoring accents and case) is sent as its id, otherwise as `brandName`. With a connection the product is sent at once, so a duplicate (409) or the daily limit (429) is answered on the form; with none, or when the request does not get through, it goes on the outbox as a `product` change carrying an id chosen on the phone, which the server keeps (CON-055). The outbox drops it on a 4xx, including a 429 without Retry-After (the daily limit, not the rate limiter), and the banner says so. "Agregar tienda" opens from Informar precio; the pin starts at the shopper's location and moves by tap or drag on a phone, address, city and country are prefilled from reverse geocoding where the phone can, and the time zone is the phone's. There is no product photo: the server ignores shoppers' image links and has no reviewed upload for products.
- **Why:** Answering refusals on the spot is better than a queue entry that fails later; offline adding matters in a shop's aisle. A shop is added in person and rarely offline, so it is not queued.
- **Revisit when:** Product photos get a reviewed upload path, or shops need adding offline.

### MCON-042 — Badges, confirm and report, and where shops show their card
- **Phase:** 8 (checkpoint 13) · **Area:** community · **Status:** accepted
- **What:** _Sin verificar_ marks community products in search and on their screen, and community shops in Informar precio; the team's entries carry nothing in lists and a _Verificado_ tick only on a shop's card. A community product shows a card with its confirmations and, for anyone but its creator, _Existe y está bien_ (a toggle) and _Reportar_, from `/v1/products/:id/viewer-say`. A shop's card opens from a price row under a product and from Mis aportes; reporting a shop happens inside that card, since a second modal over a sheet is unreliable on iOS. Price rows do not carry the badge: the pricing API does not return a shop's origin.
- **Why:** The badge is information about others' entries; marking the team's everywhere would be noise.
- **Revisit when:** Shoppers want the badge on price rows, which needs `origin` in `StorePriceResponse`.

### MCON-043 — The app tells the server its language; categories show translated
- **Phase:** 7 (checkpoint 14) · **Area:** i18n · **Status:** accepted
- **What:** Once signed in, `LanguageSync` compares the account's stored `locale` with the language showing and sends `PATCH /v1/users/me { locale }` when they differ: after choosing a language, or signing in on a phone in another one. A failure is ignored and retried on the next start. `categoryName` shows a category's translation for the app's language, else its Spanish name. The web e2e checks the server's language after switching to German and back, and the German category chips.
- **Why:** What reaches the shopper with the app closed must be in the language they use the app in (CON-056); the server only learns it from the app.
- **Revisit when:** Signing up should carry the language from the first request (today the first message could arrive before the app sends it, only in the seconds after signing up).

### MCON-044 — Compra detects the shop from the phone's position
- **Phase:** post-plan (asked by the user) · **Area:** trip, location · **Status:** accepted
- **What:** `WhereCard` on the start of Compra lists shops within 2 km of the phone's own position (not the location chip's place) and recommends the nearest within 300 m (`detectStore`, `HERE_KM`). The recommendation is preselected; _Cambiar_ offers the nearby shops, _Sin súper fijo_ and back to automatic. Starting passes `storeId` only when the shop prices in the list's currency (`pricesIn`). Informar precio labels its preselected nearest shop _Detectado_ when it is that close to the phone.
- **Why:** The user wants starting to be faster: the shop is almost always the one they are standing in, and choosing it by hand was not offered at all.
- **Revisit when:** 300 m proves too wide in dense streets (two shops on one block) or too narrow for hypermarkets with big car parks; or when the phone's position should refresh while Compra is open.

### MCON-045 — Scan to add: barcode first, prefilled from the lookup, never over the shopper's typing
- **Phase:** 9 (checkpoint 17) · **Area:** community, catalog · **Status:** accepted
- **What:** "Agregar producto" puts the barcode field first, with a button opening `ScanCodeSheet` (camera, or a typed code) that returns the code to the form. Any code of a shelf barcode's length is looked up (`useProductLookup`, `/v1/product-lookup`, CON-058): CATALOG shows "Ya está en Garner" with a link; OPEN_FOOD_FACTS fills fields through `prefillFrom`, once per code, skipping every field the shopper edited by hand; the photo is shown with its credit and sent as `photoFromLookup` unless removed. The product screen credits an Open Food Facts photo; Preferencias names the source and licences.
- **Why:** Typing name, brand and size in an aisle is the slowest part of adding a product; scanning is how people already identify products.
- **Revisit when:** The lookup should also run from the scanner itself before opening the form, or shoppers want to correct a wrong Open Food Facts entry upstream.

### MCON-047 — Creating a product from a list puts it on the list
- **Phase:** 9 (asked by the user) · **Area:** lists, community · **Status:** accepted
- **What:** The list's _Agregar producto_ search offers _Crear “…” y agregarlo_ when nothing matches, and _¿No es ninguno? Crear “…”_ under the matches. It opens `/add-product?name=…&listId=…`; in that mode a created product (`added`), a tapped suggestion, or a code already in Garner is added to the list with `useAddToList` and the form closes. ### MCON-048 — The category picker, built for a hundred aisles

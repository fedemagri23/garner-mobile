# Considerations

Deliberate limits, trade-offs and simplifications, and when to revisit them.
Notation as in the backend's `journeys/README.md`: ids are sequential and never
renumbered; a superseded entry stays and gains a **Superseded by:** line.

## Foundation

### MCON-001 — The API client is generated from the backend's committed contract
- **Phase:** 1 · **Area:** api · **Status:** accepted
- **What:** `src/api/schema.d.ts` is generated by openapi-typescript from `garner-app/openapi.json` and committed; calls go through openapi-fetch, typed by path. CI regenerates it from the backend's master and fails on any difference.
- **Why:** The backend lives in another repository; a generated client turns a breaking API change into a compile error here. openapi-fetch is a thin typed `fetch`, so there is no generated runtime code to review. openapi-typescript runs from a pinned throwaway install because it supports only TypeScript 5 and the app is on 6.
- **Revisit when:** The backend publishes the contract as a versioned package, or the app must support an older API version than master.

### MCON-002 — Only one token refresh runs at a time
- **Phase:** 1 · **Area:** session · **Status:** accepted
- **What:** The token manager refreshes ahead of expiry and after a 401, and every caller that needs a token while a refresh is running waits for that one refresh. A request that still gets a 401 after one refresh and one retry is the caller's to handle; the session is gone by then.
- **Why:** The backend rotates refresh tokens and treats a reused one as theft, revoking every session of the account. Two concurrent refreshes would sign the user out everywhere.
- **Revisit when:** The backend's rotation rules change.

### MCON-003 — The web target keeps the session in memory
- **Phase:** 1 · **Area:** session · **Status:** accepted
- **What:** On iOS and Android the refresh token is in the keychain/keystore (`expo-secure-store`). On web, which has no secure storage, it is held in memory and a reload signs out.
- **Why:** Web is a development convenience, not a product target; putting a long-lived credential in `localStorage` would make it one script injection away from theft.
- **Revisit when:** A web app becomes a product — then it wants an httpOnly-cookie session from the backend instead.

### MCON-004 — Fonts load at runtime, not embedded
- **Phase:** 1 · **Area:** theme · **Status:** accepted
- **What:** Bricolage Grotesque and Figtree load with `useFonts` from the `@expo-google-fonts` packages behind the splash screen. A font that fails to load falls back to the system font rather than blocking the app.
- **Why:** Runtime loading works in Expo Go, so development needs no custom build yet. Embedding with the `expo-font` config plugin is faster at launch but needs a development build.
- **Revisit when:** The first development build is made (phase 2 needs one for the camera) — switch to the config plugin then.

### MCON-005 — Copy is Spanish only, with no i18n layer
- **Phase:** 1 · **Area:** whole app · **Status:** accepted
- **What:** Strings are written in Spanish (es-AR) inline in the components.
- **Why:** The launch market is Buenos Aires; an i18n framework before a second language exists is structure without a user.
- **Revisit when:** A second language or market is planned — extract strings then, before the app grows further.

### MCON-006 — The API's error messages are English; screens translate what they expect
- **Phase:** 1 · **Area:** errors · **Status:** accepted
- **What:** The backend writes error messages in English. A screen passes Spanish wording for the statuses it knows the meaning of (409 on sign-up means the email is taken); anything unexpected shows the server's English message.
- **Why:** Mapping statuses per screen is enough for the handful of errors each flow can produce, and needs no backend change. Showing raw server text to Spanish-speaking users everywhere is not acceptable; translating server sentences on the client would break the first time one is reworded.
- **Revisit when:** A screen needs to tell apart two errors with the same status (validation on several fields), or a second language arrives — then the backend should send stable machine-readable error codes for the app to translate.

### MCON-007 — "Near me" is the phone's position first, the saved place second
- **Phase:** 2 · **Area:** location · **Status:** accepted
- **What:** The app asks for location once, uses a fix up to five minutes old, and falls back to the place saved in preferences when the phone says no. With both available, the chip on Inicio switches between them; the choice lasts until the app closes and is not saved. The phone's position is never written to preferences, and the radius is the one saved there (5 km by default).
- **Why:** Prices near where you stand are the point of the app, but a shopper planning from home needs their usual area too. Saving a position the person did not choose to save would be surprising, and a remembered choice is not worth a preference field yet.
- **Revisit when:** Profile settings arrive (later phase) — choosing and naming the saved place, the radius, and remembering the choice belong there.

### MCON-008 — Search results show no "desde" price
- **Phase:** 2 · **Area:** search · **Status:** deferred
- **What:** The mockup shows each result's lowest nearby price. Results show brand and package instead; prices appear on the product screen.
- **Why:** `GET /v1/products` carries no prices, and fetching a comparison per row would be twenty requests a page.
- **Revisit when:** The backend can answer a page of products with each one's lowest price near a point, in one request.

### MCON-009 — The 30-day chart ends yesterday and averages every store
- **Phase:** 2 · **Area:** product · **Status:** accepted
- **What:** The chart on a product shows the backend's daily history across all stores, which is aggregated once a day. A price that fell today shows in "Cerca tuyo" and in "Bajaron cerca tuyo" but not in the chart until tomorrow, and the chart's trend can read "subió" while today's price is lower.
- **Why:** The daily history is what the backend keeps long-term; mixing today's current prices into it would put a different kind of number on the last bar. Only stores near the shopper would need a history per store, one request each.
- **Revisit when:** Shoppers read the chart as contradicting the drop — then add a "hoy" bar from the current prices, marked as such, or ask the backend for history limited to nearby stores.

### MCON-010 — A product screen route in each tab that opens one
- **Phase:** 2 · **Area:** navigation · **Status:** accepted
- **What:** `(home)/product/[id]` and `search/product/[id]` both render the same `ProductScreen`, so a product opens on top of the tab it was tapped in and back returns there.
- **Why:** Each tab has its own stack; one shared route outside the tabs would hide the tab bar and lose the tab's place.
- **Revisit when:** A third tab needs it (lists, in phase 3) — consider Expo Router's shared groups, `(home,search,lists)`, instead of another file.

### MCON-011 — Prices are shown in their own currency, never converted
- **Phase:** 2 · **Area:** prices · **Status:** accepted
- **What:** Every amount is formatted with its own currency — "$ 1.390" for pesos (centavos only when there are some), "€ 1,15" for euros (always with cents), the ISO code for anything else — in the Spanish style the app is written in. The product screen compares each price only with the cheapest in the same currency, and its chart asks for the history in the currency of the prices near the shopper. Nothing is converted.
- **Why:** The demo data now has a Vienna neighbourhood in euros beside the Buenos Aires one in pesos. A comparison across currencies would need exchange rates, and a shopper compares the shelves in front of them, which share one currency.
- **Revisit when:** Number formatting follows the device's locale rather than the app's language, or a list or plan spans countries.

### MCON-012 — The scanner reads retail codes, matched as scanned
- **Phase:** 2 · **Area:** scanner · **Status:** deferred
- **What:** The camera looks for EAN-13, EAN-8, UPC-A and UPC-E, and the code goes to `GET /v1/products/barcode/{code}` exactly as read. A code can also be typed, which is how the web build and a phone without camera access use it.
- **Why:** These are the codes on supermarket shelves; QR and the rest are noise there. The catalog's codes are EAN-13.
- **Revisit when:** Products are catalogued from UPC-A codes. iOS reports a UPC-A as a 13-digit EAN with a leading zero and UPC-E arrives compressed, so the same product can read as two different strings — the backend should store and look up GTINs in one normalized form.

### MCON-013 — "A la lista" adds one at a time, and lists open in phase 3
- **Phase:** 2 · **Area:** lists · **Status:** accepted
- **What:** From a product, "A la lista" shows the shopper's lists with their item counts and how many of this product each already has. A tap adds one: a new line the first time, one more on the existing line after that. With no lists, it offers to create "Mi lista" in the currency of the prices nearby. The Listas tab, where lists are seen and edited, is phase 3.
- **Why:** Adding from where you find a product is the habit the mockups design for, and the counts in the sheet are enough to see that it worked. One line per product keeps the list readable and the optimizer's input simple.
- **Revisit when:** Phase 3 builds the Listas tab — quantities, notes and removal belong there.

### MCON-014 — A scanned product always opens in Buscar
- **Phase:** 2 · **Area:** navigation · **Status:** accepted
- **What:** Whichever tab the scanner was opened from, the product it finds opens on Buscar's stack.
- **Why:** Scanning is a way of searching, and a single destination keeps the scanner from needing to know who opened it.
- **Revisit when:** Shopping mode (phase 4) scans during a trip — there the product belongs on the trip, not in Buscar.

### MCON-015 — Back on Expo SDK 57 until Expo Go 58 is in the stores
- **Phase:** 2 · **Area:** tooling · **Status:** deferred
- **What:** The app was started on SDK 58 and moved back to SDK 57 (React Native 0.86, React 19.2, expo-router 57, jest 29). The only code change was the native tabs import, `expo-router/unstable-native-tabs` on 57.
- **Why:** SDK 58 shipped on 2026-10-15, and Expo said its Expo Go would reach the App Store and Play Store "within a few weeks". The developer's iPhone has Expo Go 57.0.9, which refuses an SDK 58 project, and a development build on iOS needs a paid Apple developer account. Nothing the app uses is new in 58.
- **Revisit when:** Expo Go for SDK 58 is in the App Store — then upgrade (`npx expo install expo@~58.0.0 --fix`, the import back to `expo-router/native-tabs`, `jest`/`jest-expo` to their 58 versions), run expo-doctor and every check, and mark this resolved. Store Expo Go supports only the latest SDK, so waiting too long breaks Expo Go again.

### MCON-016 — A list item's price is set when it is added
- **Phase:** 3 · **Area:** lists · **Status:** accepted
- **What:** A product added to a list gets, as its expected unit price, the cheapest price near the shopper in the list's currency at that moment; none if nobody near has reported one. The list's "Total estimado" adds those up and says how many items have no price. Prices are not refreshed afterwards.
- **Why:** The backend keeps the expected price on the item, and the real answer to "what will this cost" is the optimization in checkpoint 5, which reads current prices at real stores. A cheap, stable estimate is enough for the list screen.
- **Revisit when:** Checkpoint 5 lands — the list can then show the latest optimization's total instead, or refresh expected prices when it runs.

### MCON-017 — No manual reordering yet, and whole quantities only
- **Phase:** 3 · **Area:** lists · **Status:** deferred
- **What:** Items appear in the order they were added; − and + change the quantity by one, and − at one removes the item. The backend supports a manual order (`PUT …/items/order`) and fractional quantities, but the app offers neither.
- **Why:** Drag to reorder needs gesture work out of proportion to its value before shopping mode exists; and weighed products (0,5 kg) need a different input, not a stepper.
- **Revisit when:** Shopping mode (phase 4) — the order of a trip matters there, by store aisle, and weighed products are bought there.

### MCON-018 — The web dev server can serve stale screens after edits
- **Phase:** 3 · **Area:** tooling · **Status:** accepted
- **What:** With `npm run web` running, Metro sometimes keeps serving a screen's previous code after the file changed (screens load lazily on the web). Restarting with `npx expo start --web --clear` fixes it.
- **Why:** A development-server quirk, not app behaviour; it cost two debugging detours before being recognised.
- **Revisit when:** A newer SDK fixes lazy route invalidation — until then, restart with `--clear` before trusting what the web build shows, and before `npm run e2e:web`.
